Tak. Jeśli GridFilter ma być uniwersalnym komponentem, rozdzielenie IEnumerable i IQueryable jest zdecydowanie sensowniejsze niż próba obsłużenia obu jednym ToList().

Kluczowa zasada:

IEnumerable<T>
    → filtrujemy w pamięci

IQueryable<T>
    → budujemy Expression<Func<T,bool>>
    → filtr wykonuje provider (np. SQL)

Ale zrobiłbym to trochę inaczej niż w poprzedniej propozycji: nie używałbym dynamic ani refleksyjnego Where jako głównego mechanizmu.

Proponowana architektura
                     GridFilter
                         │
                         ▼
                  FilterDefinition
                         │
             ┌───────────┴───────────┐
             │                       │
             ▼                       ▼
     EnumerableFilter         QueryableFilter
             │                       │
             ▼                       ▼
       IEnumerable<T>          IQueryable<T>
             │                       │
             ▼                       ▼
        LINQ Objects          Expression Tree
             │                       │
             └───────────┬───────────┘
                         ▼
                   BindingSource
                         │
                         ▼
                   DataGridView

Najważniejsze jest to, że UI nie powinno wiedzieć, czy filtr działa na SQL, czy na pamięci.

1. Najpierw FilterDefinition
Obecnie masz:

Dictionary<string, string>

Ja zmieniłbym to na:

public enum FilterOperator
{
    Contains,
    Equals,
    StartsWith,
    EndsWith,
    GreaterThan,
    GreaterThanOrEqual,
    LessThan,
    LessThanOrEqual
}

i:

public sealed class FilterDefinition
{
    public string PropertyName { get; }

    public FilterOperator Operator { get; }

    public object Value { get; }

    public FilterDefinition(
        string propertyName,
        FilterOperator @operator,
        object value)
    {
        PropertyName = propertyName;
        Operator = @operator;
        Value = value;
    }
}

Teraz zamiast:

Name → "Jan"

masz:

Name
Contains
Jan

albo:

Age
GreaterThanOrEqual
18

To jest bardzo ważne, bo ten sam FilterDefinition może zostać zastosowany zarówno do IEnumerable, jak i IQueryable.

2. Wspólny interfejs
Możesz zrobić:

public interface IFilterEngine
{
    IEnumerable Apply(
        IEnumerable source,
        IReadOnlyCollection<FilterDefinition> filters);
}

Ale tutaj pojawia się problem: tracimy typ T.

Dlatego lepiej zrobić interfejs niewymagający generyczności na poziomie GridFilter, a implementacje mogą być generyczne.

Na przykład:

internal interface IFilterEngine
{
    object Apply(
        object source,
        IReadOnlyCollection<FilterDefinition> filters);
}

i implementacja:

internal sealed class EnumerableFilterEngine<T>
    : IFilterEngine
{
    public object Apply(
        object source,
        IReadOnlyCollection<FilterDefinition> filters)
    {
        IEnumerable<T> query =
            (IEnumerable<T>)source;

        // ...
        return query;
    }
}

Analogicznie:

internal sealed class QueryableFilterEngine<T>
    : IFilterEngine
{
    public object Apply(
        object source,
        IReadOnlyCollection<FilterDefinition> filters)
    {
        IQueryable<T> query =
            (IQueryable<T>)source;

        // ...
        return query;
    }
}

3. IEnumerable<T> — prosty przypadek
Dla pamięci możesz wykorzystać zwykły LINQ.

Przykładowo:

private IEnumerable<T> ApplyEnumerableFilter<T>(
    IEnumerable<T> source,
    IReadOnlyCollection<FilterDefinition> filters)
{
    IEnumerable<T> result = source;

    foreach (FilterDefinition filter in filters)
    {
        result = ApplyFilter(
            result,
            filter);
    }

    return result;
}

Natomiast ApplyFilter() może używać skompilowanego property accessor.

Czyli zamiast przy każdym rekordzie:

property.GetValue(item)

możesz przygotować accessor raz.

4. IQueryable<T> — tutaj jest najważniejsza różnica
Nie chcemy:

query.ToList()

przed filtrowaniem.

Chcemy:

query = query.Where(expression);

np. użytkownik wpisuje:

Name = "Kowalski"

i generujemy:

x => x.Name.Contains("Kowalski")

Provider może wtedy przetłumaczyć to np. na SQL.

Schemat:

IQueryable<Customer>
        │
        ▼
Expression<Func<Customer,bool>>
        │
        ▼
query.Where(...)
        │
        ▼
SQL / provider
        │
        ▼
wynik

To jest główny powód, dla którego nie należy zamieniać IQueryable na IEnumerable zbyt wcześnie.

5. Expression Builder
Zrobiłbym osobną klasę:

internal static class FilterExpressionBuilder
{
    public static Expression<Func<T, bool>>
        Build<T>(FilterDefinition filter)
    {
        ParameterExpression parameter =
            Expression.Parameter(
                typeof(T),
                "x");

        Expression property =
            Expression.PropertyOrField(
                parameter,
                filter.PropertyName);

        Expression body =
            BuildOperation(
                property,
                filter);

        return Expression.Lambda<Func<T, bool>>(
            body,
            parameter);
    }
}

I osobno:

private static Expression BuildOperation(
    Expression property,
    FilterDefinition filter)
{
    // Equals
    // Contains
    // StartsWith
    // EndsWith
    // >
    // >=
    // <
    // <=
}

Dzięki temu masz jedno miejsce odpowiedzialne za budowanie wyrażeń.

6. Przykład Contains
Dla:

new FilterDefinition(
    "Name",
    FilterOperator.Contains,
    "Jan")

builder powinien stworzyć logicznie:

x => x.Name.Contains("Jan")

A potem:

query = query.Where(expression);

Dla IEnumerable<T> możesz użyć dokładnie tego samego expression:

Func<T, bool> predicate =
    expression.Compile();

result = result.Where(predicate);

Czyli ciekawa rzecz:

Możesz mieć jeden Expression Builder dla obu przypadków
FilterDefinition
       │
       ▼
Expression<Func<T,bool>>
       │
       ├───────────────┐
       ▼               ▼
 IQueryable         IEnumerable
       │               │
 Where(expression)   Compile()
       │               │
 SQL/provider        LINQ Objects

To jest architektonicznie bardzo czyste.

7. IQueryable bez Compile()
To jest krytyczne.

Dla:

IQueryable<Customer> query

robisz:

Expression<Func<Customer, bool>> expression =
    FilterExpressionBuilder.Build<Customer>(
        filter);

query = query.Where(expression);

Nie:

query
    .AsEnumerable()
    .Where(expression.Compile());

bo wtedy odcinasz się od możliwości wykonania filtra przez bazę.

8. Jak rozpoznać źródło w GridFilter
Tutaj trzeba być ostrożnym.

DataGridView.DataSource może być:

BindingSource
IList
IEnumerable
IQueryable
DataTable
DataView

Dlatego nie robiłbym:

if (source is IQueryable)

bezpośrednio na grid.DataSource, bo bardzo często będziesz miał:

DataGridView
    ↓
BindingSource
    ↓
IQueryable<T>

czyli trzeba przejść przez BindingSource.

9. Proponuję DataSourceAdapter
To moim zdaniem będzie najlepszy element całej architektury.

internal interface IDataSourceAdapter
{
    Type ItemType { get; }

    object GetSource();

    object ApplyFilters(
        IReadOnlyCollection<FilterDefinition> filters);
}

Implementacja dla IEnumerable:

internal sealed class EnumerableDataSourceAdapter<T>
    : IDataSourceAdapter
{
    private readonly IEnumerable<T> source;

    public EnumerableDataSourceAdapter(
        IEnumerable<T> source)
    {
        this.source = source;
    }

    public Type ItemType => typeof(T);

    public object GetSource()
        => source;

    public object ApplyFilters(
        IReadOnlyCollection<FilterDefinition> filters)
    {
        IEnumerable<T> result = source;

        foreach (FilterDefinition filter in filters)
        {
            Expression<Func<T, bool>> expression =
                FilterExpressionBuilder.Build<T>(filter);

            result = result.Where(
                expression.Compile());
        }

        return result;
    }
}

I analogicznie:

internal sealed class QueryableDataSourceAdapter<T>
    : IDataSourceAdapter
{
    private readonly IQueryable<T> source;

    public QueryableDataSourceAdapter(
        IQueryable<T> source)
    {
        this.source = source;
    }

    public Type ItemType => typeof(T);

    public object GetSource()
        => source;

    public object ApplyFilters(
        IReadOnlyCollection<FilterDefinition> filters)
    {
        IQueryable<T> result = source;

        foreach (FilterDefinition filter in filters)
        {
            Expression<Func<T, bool>> expression =
                FilterExpressionBuilder.Build<T>(filter);

            result = result.Where(expression);
        }

        return result;
    }
}

10. Co wtedy dzieje się w GridFilter
GridFilter przestaje zawierać logikę:

Convert.ToString(...)
property.GetValue(...)
source.Cast<object>()

Zamiast tego:

private IDataSourceAdapter _dataSource;

i:

private void ApplyFilter(FilterContext context)
{
    if (context == null)
        return;

    object filtered =
        context.DataSource.ApplyFilters(
            context.Filters);

    context.Source.DataSource = filtered;

    context.Source.ResetBindings(false);
}

To jest dużo czystsze.

11. Jedna rzecz, którą zrobiłbym inaczej niż w Twojej obecnej klasie
Nie przechowywałbym:

Dictionary<string, string>

tylko:

Dictionary<string, FilterDefinition>

albo:

List<FilterDefinition>

Wtedy możesz później łatwo zrobić:

Name        Contains        "Jan"
Age         >=              18
IsActive    Equals          true
Created     >=              2026-01-01

i masz już fundament pod bardziej zaawansowany filtr.

12. Ostateczna struktura
Ja bym docelowo rozbił Twój jeden plik na:

GridFilter/
│
├── GridFilter.cs
│
├── FilterContext.cs
│
├── FilterDefinition.cs
│
├── FilterOperator.cs
│
├── FilterExpressionBuilder.cs
│
├── IDataSourceAdapter.cs
│
├── EnumerableDataSourceAdapter.cs
│
└── QueryableDataSourceAdapter.cs

I odpowiedzialności:

GridFilter
   │
   ├── UI
   ├── TextBox / ComboBox
   ├── eventy DataGridView
   └── zarządzanie filtrem
             │
             ▼
      FilterDefinition
             │
             ▼
   FilterExpressionBuilder
             │
       ┌─────┴─────┐
       ▼           ▼
 IEnumerable    IQueryable
       │           │
       ▼           ▼
 Compile()       Expression
       │           │
       ▼           ▼
 LINQ memory     Provider/SQL

To jest wariant, który wybrałbym dla Twojego projektu. Szczególnie dlatego, że pozwala zachować jedną definicję filtra i jeden ExpressionBuilder, a różnicę między filtrowaniem w pamięci i filtrowaniem przez provider zamknąć w adapterach.

Jeśli chcesz, mogę w następnym kroku przepisać Twój obecny GridFilter 1:1 na tę architekturę, tak żebyś dostał gotowy kod C# do wklejenia, a nie tylko szkic.
