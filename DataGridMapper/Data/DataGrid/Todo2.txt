Cel końcowy
Chcemy dojść do takiej architektury:

DataGridView
    │
    ▼
 GridFilter
    │
    ├── UI filtrów
    ├── obsługa kolumn
    ├── debounce
    └── FilterDefinition
              │
              ▼
     FilterExpressionBuilder
              │
       ┌──────┴──────┐
       ▼             ▼
 IEnumerable      IQueryable
       │             │
       ▼             ▼
 LINQ in-memory   Expression Tree
       │             │
       ▼             ▼

       │             │
       └──────┬──────┘
              ▼
        BindingSource
              │

Etap 0 — zabezpieczenie obecnego kodu
Cel: mieć punkt odniesienia przed refaktoryzacją.

Przygotujemy testowy scenariusz z:

List<Customer>
BindingList<Customer>
BindingSource

oraz przykładowymi kolumnami:

Id
Name
Age
IsActive
Created

Sprawdzamy:

Enable()

Disable()

filtrowanie jednej kolumny

filtrowanie kilku kolumn

bool

null

zmianę szerokości kolumn

scrollowanie

sortowanie

ponowne Enable()

Efekt: wiemy, co obecnie działa i czego nie możemy przypadkowo zepsuć.

Etap 1 — wyciągnięcie FilterDefinition
Obecnie mamy:

Dictionary<string, string>

Zmienimy to na:

public enum FilterOperator
{
    Contains,
    Equals,
    StartsWith,
    EndsWith,
    GreaterThan,
    GreaterThanOrEqual,
    LessThan,
    LessThanOrEqual
}

oraz:

public sealed class FilterDefinition
{
    public string PropertyName { get; }

    public FilterOperator Operator { get; }

    public object Value { get; }

    public FilterDefinition(
        string propertyName,
        FilterOperator @operator,
        object value)
    {
        PropertyName = propertyName;
        Operator = @operator;
        Value = value;
    }
}

Dlaczego?
Bo:

"Age" → "18"

jest bardzo ubogą informacją.

Natomiast:

Age
GreaterThanOrEqual
18

daje nam wszystko, czego później potrzebujemy zarówno dla IEnumerable, jak i IQueryable.

Etap 2 — FilterExpressionBuilder
Budujemy jedną klasę odpowiedzialną za tworzenie:

Expression<Func<T, bool>>

Przykład:

Name Contains "Jan"

staje się:

x => x.Name.Contains("Jan")

A:

Age >= 18

staje się:

x => x.Age >= 18

Dlaczego robimy to przed rozdzieleniem źródeł?
Bo potem ten sam expression wykorzystamy w dwóch miejscach:

Expression<Func<T,bool>>
        │
        ├── IEnumerable
        │       ↓
        │   Compile()
        │       ↓
        │   LINQ
        │
        └── IQueryable
                ↓
             Where()
                ↓
             provider

To będzie jeden z najważniejszych elementów całej refaktoryzacji.

Etap 3 — oddzielenie IEnumerable
Tworzymy:

EnumerableDataSourceAdapter<T>

Odpowiada wyłącznie za dane znajdujące się w pamięci.

Przykład:

List<Customer>
       ↓
EnumerableDataSourceAdapter<Customer>
       ↓
FilterExpressionBuilder
       ↓
Expression
       ↓
Compile()
       ↓
Where()
       ↓
List<Customer>

Ważne
Nie będziemy robić przy każdym TextChanged:

OriginalDataSource
    .Cast<object>()
    .ToList();

Źródło zostanie przygotowane raz, a kolejne filtry będą wykonywane na właściwym źródle.

Etap 4 — oddzielenie IQueryable
Tworzymy:

QueryableDataSourceAdapter<T>

Tutaj nie wykonujemy ToList() przed filtrowaniem.

Czyli:

IQueryable<Customer> query;

otrzyma:

query = query.Where(expression);

Dzięki temu provider może wykonać filtr po swojej stronie.

Schemat:

IQueryable<Customer>
       ↓
Where(x => x.Name.Contains("Jan"))
       ↓
provider
       ↓
SQL / inne źródło
       ↓
wynik

To jest kluczowa różnica względem obecnej implementacji.

Etap 5 — IDataSourceAdapter
Dopiero kiedy oba mechanizmy będą działały osobno, wyciągamy wspólny interfejs:

internal interface IDataSourceAdapter
{
    Type ItemType { get; }

    object ApplyFilters(
        IReadOnlyCollection<FilterDefinition> filters);
}

Wtedy GridFilter nie musi wiedzieć:

czy to List<T>?
czy BindingList<T>?
czy IQueryable<T>?

Dostaje po prostu adapter.

Etap 6 — obsługa BindingSource
To będzie osobny etap, ponieważ tutaj jest najwięcej potencjalnych problemów.

Musimy obsłużyć sytuację:

DataGridView
    ↓
BindingSource
    ↓
List<T>

oraz:

DataGridView
    ↓
BindingSource
    ↓
IQueryable<T>

Nie możemy zakładać, że:

grid.DataSource

jest bezpośrednio kolekcją.

Będziemy musieli rozpoznać rzeczywiste źródło za BindingSource.

Etap 7 — przebudowa FilterContext
Obecnie:

public object OriginalDataSource { get; set; }

public BindingSource Source { get; set; }

public Dictionary<string, string> Values { get; }

Docelowo coś w tym stylu:

private sealed class FilterContext
{
    public DataGridView Grid { get; set; }

    public BindingSource BindingSource { get; set; }

    public object OriginalDataSource { get; set; }

    public IDataSourceAdapter DataSource { get; set; }

    public Panel FilterPanel { get; set; }

    public Dictionary<string, FilterDefinition> Filters { get; }
        = new Dictionary<string, FilterDefinition>(
            StringComparer.OrdinalIgnoreCase);

    public Dictionary<int, Control> Controls { get; }
        = new Dictionary<int, Control>();
}

W tym momencie GridFilter będzie już znacznie prostszy.

Etap 8 — przebudowa ApplyFilter()
Obecnie jest tam sporo logiki dotyczącej danych.

Docelowo chcemy, żeby:

private void ApplyFilter(FilterContext context)
{
    object result =
        context.DataSource.ApplyFilters(
            context.Filters.Values.ToList());

    context.BindingSource.DataSource = result;

    context.BindingSource.ResetBindings(false);
}

Czyli GridFilter mówi tylko:

„Mam takie filtry. Zastosuj je.”

Nie interesuje go, jak.

Etap 9 — typy danych
Po działającym podstawowym filtrowaniu dodamy właściwe traktowanie typów:

string
    → Contains

bool
    → Equals

enum
    → Equals / ComboBox

int / decimal / double
    → =, >, >=, <, <=

DateTime
    → =, >, >=, <, <=

nullable
    → null / not null

Dzięki temu przestaniemy robić wszędzie:

Convert.ToString(...)

Etap 10 — debounce
Dopiero po uporządkowaniu filtrowania danych.

Obecnie:

K
 ↓
filter

Ko
 ↓
filter

Kow
 ↓
filter

Kowa
 ↓
filter

Docelowo:

K
Ko
Kow
Kowa
Kowalski
   ↓
 250 ms
   ↓
filter

To będzie szczególnie istotne przy IQueryable, żeby nie wysyłać zapytania do bazy przy każdym naciśnięciu klawisza.

Etap 11 — kolumny dynamiczne
Następnie dodamy obsługę:

ColumnAdded
ColumnRemoved
ColumnStateChanged
ColumnWidthChanged
ColumnDisplayIndexChanged

Obecnie filtry są tworzone tylko raz.

Docelowo:

dodano kolumnę
      ↓
utwórz filtr

usunięto kolumnę
      ↓
usuń filtr

ukryto kolumnę
      ↓
ukryj filtr

Etap 12 — layout
Dopiero na końcu poprawiłbym panel.

Obecne rozwiązanie:

Parent
 ├── FilterPanel
 └── DataGridView

jest funkcjonalne, ale dość kruche.

Możemy później zrobić:

GridFilterHost
 ├── FilterPanel
 └── DataGridView

i wtedy:

GridFilterHost
       ↓
 ┌───────────────┐
 │ FilterPanel   │
 ├───────────────┤
 │ DataGridView  │
 └───────────────┘

To znacznie uprości pozycjonowanie kontrolek filtrujących.

Każdy etap powinien kończyć się działającym kodem.

Przykładowo po etapie 4:

List<Customer>
    ↓
GridFilter
    ↓
filtrowanie
    ↓

IQueryable<Customer>
    ↓
GridFilter
    ↓
filtrowanie
    ↓

Dzięki temu, jeżeli coś się zepsuje, wiemy dokładnie, w którym etapie.

Docelowy rezultat
Chcemy, żeby użytkownik klasy nadal robił mniej więcej:

GridFilter filter = new GridFilter(dataGridView);

filter.Enable();

i nic nie musiał wiedzieć o:

IEnumerable
IQueryable
Expression
BindingSource
LINQ
EF

Cała ta złożoność zostaje wewnątrz biblioteki.

A z punktu widzenia użytkownika:

List<T>             → działa
BindingList<T>      → działa
BindingSource       → działa
IQueryable<T>       → działa
bool                → działa
string              → działa
liczby              → działają
DateTime            → działa
nullable            → działa

Najpierw proponuję zrobić etap 1–2 (FilterDefinition + FilterExpressionBuilder). To będzie fundament całej dalszej pracy i na tym możemy potem budować kolejne etapy bez przepisywania wszystkiego ponownie.
