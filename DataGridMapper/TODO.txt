Tak. To jest moim zdaniem najważniejszy kierunek rozwoju architektury MC.Data.DataGrid.

Obecnie GridProperty, GridFilter i CustomColumn rozwiązują swoje problemy osobno, ale wszystkie w praktyce potrzebują tej samej informacji:

„Co wiadomo o właściwości modelu i jak DataGrid ma ją traktować?”

Warto więc wprowadzić osobną warstwę metadata, która stanie się wspólnym źródłem prawdy.

1. Problem obecnej architektury
Dzisiaj informacje o właściwości są rozproszone.

Przykładowo:

[GridView(
    "Cena",
    format: "N2",
    columnType: GridViewAttribute.EColumnType.Number)]
public decimal Price { get; set; }

GridProperty interpretuje ten atrybut.

Natomiast GridFilter niezależnie dostaje:

new FilterDefinition(
    "Price",
    FilterOperator.GreaterThan,
    100m);

i sam próbuje ustalić:

Price
 ↓
PropertyInfo?
 ↓
Type?
 ↓
Nullable?
 ↓
Enum?
 ↓
string?

A CustomColumn ma jeszcze własne informacje dotyczące:

TData
TView
Id
cache
renderowanie

Czyli obecnie kilka części biblioteki osobno odkrywa właściwości modelu.

To jest dobre na początku projektu, ale wraz z rozwojem biblioteki zaczyna powodować duplikację logiki.

3. PropertyMetadata
Zacząłbym od najważniejszej klasy.

public sealed class PropertyMetadata
{
    public PropertyInfo Property { get; }

    public string Name
    {
        get { return Property.Name; }
    }

    public Type PropertyType
    {
        get { return Property.PropertyType; }
    }

    public Type UnderlyingType
    {
        get
        {
            return Nullable.GetUnderlyingType(PropertyType)
                ?? PropertyType;
        }
    }

    public bool IsNullable
    {
        get
        {
            return !PropertyType.IsValueType
                || Nullable.GetUnderlyingType(PropertyType) != null;
        }
    }

    public bool IsEnum
    {
        get { return UnderlyingType.IsEnum; }
    }

    public bool IsString
    {
        get { return UnderlyingType == typeof(string); }
    }

    public bool IsBoolean
    {
        get { return UnderlyingType == typeof(bool); }
    }

    public bool IsNumeric
    {
        get
        {
            switch (Type.GetTypeCode(UnderlyingType))
            {
                case TypeCode.Byte:
                case TypeCode.SByte:
                case TypeCode.Int16:
                case TypeCode.UInt16:
                case TypeCode.Int32:
                case TypeCode.UInt32:
                case TypeCode.Int64:
                case TypeCode.UInt64:
                case TypeCode.Single:
                case TypeCode.Double:
                case TypeCode.Decimal:
                    return true;

                default:
                    return false;
            }
        }
    }

    public PropertyMetadata(PropertyInfo property)
    {
        if (property == null)
            throw new ArgumentNullException("property");

        Property = property;
    }
}

Ale nie zatrzymywałbym się na takim DTO.

Warto, żeby PropertyMetadata reprezentowało rzeczywiście semantykę właściwości.

Lepiej:

PropertyMetadata

Dzięki temu odpowiedzialności pozostają rozdzielone.

6. GridViewMetadata
Twój obecny GridViewAttribute powinien nadal istnieć.

Nie usuwałbym atrybutu.

Zrobiłbym:

GridViewAttribute
       │
       ▼
MetadataProvider
       │
       ▼
GridViewMetadata
       │
       ▼
GridProperty

Czyli atrybut jest deklaracją, a metadata jest zinterpretowanym opisem.

Przykładowo:

public sealed class GridViewMetadata
{
    public bool IsConfigured { get; }

    public bool Ignore { get; }

    public bool Visible { get; }

    public bool AllowEdit { get; }

    public string HeaderName { get; }

    public string ColumnName { get; }

    public string Format { get; }

    public GridViewAttribute.EColumnType ColumnType { get; }

    public string ActionName { get; }
}

Wtedy GridProperty nie musi już robić:

property.GetCustomAttribute<GridViewAttribute>()

w wielu miejscach.

Robi tylko:

metadata.GridView

7. To samo dla filtrowania
Tu jest jeszcze większa korzyść.

Obecnie FilterExpressionBuilder ma logikę:

if (valueType.IsEnum)

else if (valueType == typeof(Guid))

else
{
    Convert.ChangeType(...)
}

oraz:

Contains
    → string

StartsWith
    → string

GreaterThan
    → porównywalny typ

Część tej wiedzy powinna pochodzić z metadata.

Przykładowo:

PropertyMetadata metadata =
    provider.GetProperty<T>("Price");

i:

metadata.PropertyType
metadata.UnderlyingType
metadata.IsNullable
metadata.IsEnum
metadata.IsString
metadata.IsNumeric

8. FilterExpressionBuilder staje się prostszy
Zamiast:

var property = Expression.PropertyOrField(
    parameter,
    filter.PropertyName);

var value = CreateValueExpression(
    property.Type,
    filter.Value);

możemy mieć:

var metadata =
    _metadataProvider.GetProperty<T>(
        filter.PropertyName);

var property =
    metadata.CreateExpression(parameter);

var value =
    _valueConverter.Convert(
        filter.Value,
        metadata);

To bardzo dobrze rozdziela odpowiedzialności.

FilterExpressionBuilder
        │
        ├── jaka właściwość?
        │       ↓
        │   MetadataProvider
        │
        ├── jaka wartość?
        │       ↓
        │   ValueConverter
        │
        └── jaki operator?
                ↓
          ComparisonBuilder

15. Metadata dla CustomColumn
Tutaj też widzę duży potencjał.

Obecnie CustomColumn<TData,TView> ma swoją konfigurację.

Można stworzyć:

public sealed class CustomColumnMetadata
{

    public Func<object, object> KeySelector { get; }

Ale tutaj zachowałbym ostrożność.

Dlatego docelowo widziałbym dwa poziomy:

    └── CustomColumnMetadata

To rozróżnienie będzie bardzo przydatne.

16. Trzy rodzaje metadata
Moim zdaniem docelowy model powinien wyglądać tak:

Metadata
│
├── TypeMetadata
│
├── PropertyMetadata
│
├── GridMetadata
│
└── GridColumnMetadata

TypeMetadata
Opisuje klasę:

Product
 ├── Properties
 ├── Id
 ├── ...
 └── CustomColumn capabilities

PropertyMetadata
Opisuje właściwość CLR:

Price
 ├── PropertyInfo
 ├── Type
 ├── Nullable
 ├── Enum
 └── GridView

GridMetadata
Opisuje konfigurację całego gridu.

GridColumnMetadata
Opisuje konkretną kolumnę DataGridView.

To jest ważne, ponieważ:

nie każda kolumna DataGridView musi być bezpośrednim odwzorowaniem jednej właściwości CLR.

Przykład:

Button "Edytuj"

może być kolumną UI, mimo że nie reprezentuje realnej właściwości modelu.

17. To rozwiązuje problem Button
Obecnie masz:

[GridView(
    "Edytuj",
    columnType: EColumnType.Button,
    actionName: "Edit")]
public string Edit { get; set; }

To jest trochę sztuczne.

Edit niekoniecznie jest rzeczywistą daną.

Metadata pozwala w przyszłości zrobić:

[GridButton(
    "Edytuj",
    ActionName = "Edit")]

bez:

public string Edit { get; set; }

czyli:

Model property
      │
      └── data column

Grid metadata
      │
      └── UI-only column

To byłaby bardzo naturalna ewolucja biblioteki.

21. Największa korzyść
Najważniejsza zmiana nie polega na tym, że powstanie kilka nowych klas.

Chodzi o zmianę przepływu informacji.

Obecnie
GridProperty
    ↓
Reflection

GridFilter
    ↓
Reflection / Type

CustomColumn
    ↓
własna konfiguracja

czyli:

trzy miejsca interpretują model.

Po zmianie
             Model
               │
               ▼
        MetadataProvider
               │
               ▼
        ┌──────────────┐
        │   Metadata   │
        └──────┬───────┘
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
      Grid   Filter  Custom

czyli:

jedno miejsce interpretuje model, a reszta korzysta z gotowej informacji.

To jest moim zdaniem architektonicznie największy krok, jaki możesz teraz zrobić.

22. I zrobiłbym to etapami
Nie przepisywałbym od razu całej biblioteki.

Etap 1 — fundament
Wprowadzić:

IMetadataProvider
ReflectionMetadataProvider
TypeMetadata
PropertyMetadata

i cache.

Etap 2 — GridProperty
Przenieść interpretację:

GridViewAttribute

do:

GridViewMetadata

i zmusić GridProperty do korzystania z metadata.

Etap 3 — GridFilter
Usunąć z FilterExpressionBuilder część odpowiedzialną za odkrywanie typu.

Wprowadzić:

PropertyMetadata
+
FilterValueConverter

Etap 4 — CustomColumn
Opisać konfigurację CustomColumn jako metadata kolumny, ale nie mieszać jej bezpośrednio z CLR PropertyMetadata.

Etap 5 — ColumnFactory
Wyciągnąć tworzenie DataGridViewColumn z GridProperty.

Wtedy GridProperty staje się przede wszystkim orkiestratorem.

23. Jeszcze jedna rzecz, którą warto zrobić od początku
Wprowadziłbym jawne rozróżnienie między PropertyMetadata a ColumnMetadata.

To może wydawać się drobiazgiem, ale uchroni bibliotekę przed dużym problemem w przyszłości:

PropertyMetadata
    = "co jest w modelu?"

ColumnMetadata
    = "jak chcę to pokazać w gridzie?"

To daje bardzo mocną podstawę do późniejszego dodania:

Sorting
Grouping
Filtering
Searching
Export
Validation
Formatting
Conditional formatting
Column visibility
Column ordering

bez rozpychania GridViewAttribute i PropertyMetadata w nieskończoność.

To właśnie tę granicę zaprojektowałbym teraz, zanim zacząłbym refaktoryzować istniejący kod.
